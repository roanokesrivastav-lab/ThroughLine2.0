# Decisions

Judgment calls not settled by the brief, one line of reasoning each. Newest at the bottom.

1. **Next.js over Expo.** The build brief specified Next.js App Router + Vercel + Serwist; the later plan preferred Expo. The user asked to keep the original stack and take features from the plan, so Next.js it is. Going native later means a separate shell, not a rewrite of the engines, which are plain TypeScript.
2. **Serwist via the webpack bundler.** `@serwist/next` is documented against webpack; `next dev --webpack` / `next build --webpack` is the supported path on Next 16. The service worker is disabled in development.
3. **Client-side data via route handlers + TanStack Query**, not server components with direct DB reads. One data path, easier caching and invalidation after writes, and the API doubles as the contract a native client would use.
4. **Shared catalog is written only with the service role.** `media_items` is readable by any signed-in user and written by server code, so users cannot corrupt each other's metadata. Everything user-owned is RLS-scoped by `user_id`.
5. **One entry per user per media item.** Re-listens and re-reads are captured as additional reactions and resurfacing responses, not duplicate entries. Keeps history and phases honest.
6. **Extraction queue = a pending row + `after()` + daily cron.** No external queue. Saves return immediately; extraction runs after the response and any failures are retried by the cron with an attempt cap.
7. **Vocabulary v1** has five tag groups (tone, register, texture, aftertaste, theme) and three scalars (intensity, ache, pace). Themes and aftertastes carry the most weight in similarity because they bridge media best; register and texture are secondary.
8. **Deterministic mock extractor is a lexicon**, not a random stub, so the app is genuinely usable without an API key and results are explainable. The Claude extractor uses structured output against the same Zod schema and the same vocabulary.
9. **Claude model defaults to `claude-opus-5`** (the current guidance default), with `ANTHROPIC_MODEL` as an override for cost. Effort is set to `low` for both extraction and explanation because the tasks are small.
10. **Canon list is hand-written** (about 100 titles) with an `encounter_weight` used only to order onboarding cards and a faint `feel_prior` so a "Loved it" tap already carries signal. Priors are blended at low weight and always lose to the user's own words.
11. **Recommendation candidates come from three popularity-free sources:** the user's own backlog, the canon list (which carries priors), and other works by creators of things they loved (structural bridge, inherits a faded version of the loved entry's vector). No "people also liked", no trending, no discover-by-popularity.
12. **Private score weight in scoring is capped at ±0.05**, as a sort nudge on the bridge anchor only. Tests assert this.
13. **Books and time budgets.** A reading session is flexible, so books pass any budget ≥ 40 minutes and are excluded below that; "short to read" excludes books over roughly 300 pages (1.6 min/page heuristic).
14. **Phases are reconciled by fingerprint.** Re-detection updates existing phases and keeps user labels; phases that stop holding are deleted unless renamed. Confidence maps to tentative / likely / strong in the UI.
15. **Seasons are northern-hemisphere** in phase labels ("Winter 2025"). Easy to revisit.
16. **Feeling clusters need ≥4 loved entries in 60 days, ≥3 agreeing on a dominant attribute** and at least half the window. Labels are "Season Year: noun and noun".
17. **Resurfacing anti-annoyance:** no entry surfaces twice within 30 days, no push while a card is unanswered (14-day window), snooze respected, cadence off by default until opt-in, and the home card is pull-based so the feature works without push.
18. **Home recommendations are cached for 24h** in `query_sessions` (kind `home`) keyed by library size, so the AI explainer is not called on every visit.
19. **External scores are fetched only on an explicit tap** in entry detail, via an adapter method; never on render, never in lists.
20. **Demo library is seeded into the signed-in user's own account** from Settings (idempotent), rather than a separate demo account, so RLS and the real code path are exercised.
21. **Onboarding "Loved it" creates a completed entry with a `loved` reaction dimension and no note**; "Seen it" creates a completed entry with no reaction; "Never heard of it" is recorded only in `onboarding_prefs` so the card does not come back.
22. **`/search` redirects to `/add`.** One logging surface is less to learn.
23. **A rule-based tag baseline ships before the semantic attribute engine.** Founder's call: judge a simple, readable engine against real use first, then layer the sentiment matching on. `docs/RECOMMENDATIONS.md` §1–§12 becomes Stage 1.5.
24. **Tags are derived from taps, not declared in a form.** The original proposal was a preferences questionnaire. Genre tags cannot bridge media, so a declared-genre engine structurally cannot produce the product's signature line, and a setup form contradicts "low friction beats completeness". The onboarding canon pass already yields a weighted tag and creator profile on day one, from taps. Pinning and muting in Settings are the only declared inputs and both are optional.
25. **Tag specificity, not a binary stoplist.** A shared "indie folk" says far more than a shared "rock", so tags carry a 0..1 specificity used at match time. Only genuinely empty tags ("drama", "fiction", "classic") are dropped outright. Phase detection now shares this via `isTooBroadForPhases`, replacing its own hardcoded list.
26. **Tag families are walked one level only.** "indie folk" credits "folk" at 0.6. Walking further compounds the decay into noise, and the parent graph is hand-written and shallow on purpose.
27. **Overlap is coverage × confidence.** Coverage is the specificity-weighted mean of how much the profile likes the candidate's own tags, already a true 0..1 reading. Confidence rises with the number of distinct matches from a 0.65 floor. An earlier saturating-sum formula scored a good single-tag match at 0.10, which made the tag layer inert; this was caught by reading real engine output, not by a test.
28. **The rules/feeling blend is weighted by evidence, not fixed.** `feelingWeight(notes)` runs 0.15 at zero notes to 0.80 at twelve. The tag layer leads at cold start and recedes on its own as the user writes. This is what makes the baseline a seam rather than a dead end.
29. **The route is derived from whichever component dominated**, never chosen by hand, so an explanation cannot claim a reason the arithmetic did not support.
30. **Components re-normalise over the ones with evidence.** A candidate the feeling layer cannot read (most live catalogue results, which have no extracted attributes) would otherwise be structurally capped below the hand-written canon, quietly making the engine canon-only.
31. **Taste prefs live in `users.onboarding_prefs.taste`, with no migration.** Migration 0001 has not yet been run against a live project; adding 0002 before the first is exercised is premature. If the dismissed list outgrows a jsonb blob, that is the signal to promote it to a table.
32. **"Not for me" is item-scoped and never widens.** It hides that one candidate. It does not penalise the creator, the genre or the kind, because one rejection is not evidence about a whole category of things.
33. **Email confirmation is bypassed in development only, via a server route.** TEMPORARY, founder's call on 2026-09-11: confirmation emails were not arriving and were blocking all live testing. `POST /api/dev/confirm` uses the service role key server-side to create the account already confirmed (or confirm an existing one), and the sign-in screen calls it on sign-up and on a "not confirmed" sign-in failure. It returns 404 when `NODE_ENV === "production"`, so the bypass cannot exist in a deployed build, and the service role key never reaches the browser. The real fix is to turn "Confirm email" off (or fix SMTP) in the Supabase dashboard; delete this route and the sign-in branches once email delivery works.
34. **Web novels, light novels and manga are books with a `book_kind`, not a sixth category.** PRD §5 locks five categories. `metadata.book_kind` carries the distinction for display and future matching. A real sixth category is the founder's call, outside a coding session.
35. **"Add it yourself" items are keyed to the user who typed them** (`source: "manual"`, `external_id: <user_id>:<category>:<slug>`). The shared catalogue would otherwise merge two people's hand-typed titles, and a user's typed text is their data. The server strips any image, tags or feeling prior from a manual item: nothing is claimed about it beyond what was typed.
36. **Canon cards gained "Want to" and "Not sure".** Founder feedback: having heard of something without having seen it is important signal. "Want to" creates a `want` entry and never downgrades an existing finished one. "Not sure" is recorded only in `onboarding_prefs.canon`, like "Never heard", so it creates no entry and no weight, but remembers the title was encountered.
37. **Search in "Everything" ranks by text match, not interleave alone.** Exact title, then all meaningful words present (ignoring "the/of/a"), then how much of the title the query covers, then each provider's own first pick. When three or more titles match, non-matching ones are dropped as noise. This is text relevance only; no provider popularity field is read. A category chip bypasses the merge and shows that provider's list.
38. **Spotify is the first music adapter when keys are present, then MusicBrainz, then canon.** Client-credentials only, server-side, token cached in memory. It gives identity, album, length and art. Its popularity field is never read or stored (PRD §2.4), and it offers new apps no audio features or genres, so music tag coverage from Spotify results is empty; Stage 3's item profiles are the answer to that. Search is capped at 10 per request by Spotify for this app tier. Remasters and re-releases of one song by one artist collapse, preferring the original album.
39. **Adapters now fall through in order on empty or error** (`adaptersFor`), rather than jumping straight to canon, so a Spotify outage still searches MusicBrainz.
40. **Dates are stored as vague as they were given.** Migration 0002 adds `consumed_precision` (day/month/season/year/range) and `consumed_until`. "~2019" is Jan 1–Dec 31 2019 with precision `year`; "as a teen" is a `range` computed from an optional birth year kept in `onboarding_prefs.birth_year`. Nothing is converted into a false exact date.
41. **Undated onboarding and canon entries stay undated.** The day someone tapped "Loved it" says nothing about when they watched it, and stamping it put a lifetime of favourites into one month. Migration 0002 clears `consumed_at` on onboarding picks only where it still equals the creation day (the old default). Plain logs still default to today, because "what did you just finish" usually means today.
42. **Phases and eras skip what they cannot honestly place.** Time-window phases (creator runs, category stretches, genre runs, feeling clusters) only use entries whose span is at most 100 days (a season or finer); album rollups still use everything, since they have no time window. Taste evolution and History's date filters skip undated entries. Ordering uses the middle of a span.
43. **Timeline is its own tab** (`/timeline`), founder's request from the original concept. Year bands newest first, zoomable to seasons, cover art sorted by the user's own affinity, detected phases overlapping each band, and an "undated" shelf to place things in one step. No counts, no streaks, no charts. Mobile nav is now six items.
44. **Duplicate "Loved it" reactions are skipped.** Live data showed onboarding picks with two `{loved: true}` reactions from going Back and re-picking, which doubled their weight. A note-less reaction whose taps are all already recorded on that entry is not inserted again. Onboarding picks are also now read back from the server, so going Back no longer forgets them.
45. **NVIDIA is an optional AI provider.** NVIDIA's OpenAI-compatible hosted endpoint is selected explicitly with `AI_PROVIDER=nvidia`; `openai/gpt-oss-20b` is the default because its free endpoint is currently available, while the larger free `gpt-oss-120b` endpoint is deprecated. The raw note remains server-side and the deterministic mock remains the fallback. *(Added by Codex; moved here from a duplicate number 32.)*
46. **NVIDIA's default model is Nemotron 3 Super, not gpt-oss-20b.** Tested 2026-09-13 on the founder's real Hunter x Hunter note. gpt-oss-20b returned nothing at 2,048 tokens (its thinking used the whole allowance), and once given room it read the same note two opposite ways across two runs ("bleak, loud, survival" then "warm, comforting, love, memory"). `nvidia/nemotron-3-super-120b-a12b` gave near-identical, sensible readings both times (epic, propulsive, dense, fierce; power, survival, violence) and correctly ignored "quiet", at 15–20 s per note with an occasional minute-plus stall. Extraction runs after the response, so latency is acceptable; the client now has a 120 s timeout, sends `reasoning_effort: low` to gpt-oss models, allows 8,192 tokens, extracts the JSON object from surrounding prose, and reports a clear error when a reasoning model runs out of room. DeepSeek V4 Flash hung past five minutes; Kimi is not enabled on this account.
47. **Notes go to NVIDIA-hosted models when `AI_PROVIDER=nvidia`.** PRD §7 names the Claude API as the server-side model; it is not a locked section, and the founder chose NVIDIA credits. The privacy property that matters is kept: only the server calls the model and the key never reaches the client. Settings now says plainly that notes are sent to NVIDIA to be read. NVIDIA's hosted catalogue is aimed at development and prototyping; check its terms before any wider use.
48. **"Re-read my notes" re-extracts only readings made by a different extractor.** Switching providers otherwise leaves every old lexicon reading in place forever (rows are `done`). The route resets those `extracted_attributes` rows to pending, clears the day's cached home recommendations, and works through them after the response. Raw notes are untouched. Pressing it twice queues nothing new.
49. **Film, TV, anime and books are scored story-first.** Founder's call, 2026-09-15. Story and themes (`docs/ATTRIBUTES.md` 1B) weigh 0.40, feeling and mood 0.20, form fit 0.15, creator 0.10, current phase 0.10, novelty 0.05 (`docs/RECOMMENDATIONS.md` §14). The founder's reason: story and themes can be profiled well from catalogue descriptions and the AI's knowledge of a work, while feeling is secondary. Anime goes with TV because both are logged as series (PRD §5).
50. **All five media get profiled; only four get matched.** Music is profiled now (energy, tempo, vocal, instrumentation, production, lyric themes) so the data exists. Music matching waits until the founder settles its specifics. Spotify gives no audio features, so these traits are AI-written at a confidence of 0.5 or lower.
51. **Readings of a note may carry negative weights; item profiles may not.** "There's no quiet feeling" records `register.quiet = -0.6`, and a strong negative penalises matches. An item profile only says what is present.
52. **`ending` attributes are profiled but never shown.** They are spoilers. They may shape matching, but no explanation, portrait or card names them.
53. **Every attribute is a named word from a closed list, with a source and confidence.** That keeps PRD §9 (no semantic or vector search) and makes every match inspectable. Profiles describe what a work is; no attribute reads reception, ratings, awards or popularity.
54. **The recommendation model is a hand-tuned weighted score now, with per-user logistic regression later.** The regression learns the same named component weights from one person's own answers, is regularised toward the hand-tuned weights, stays within a fixed band, and starts after roughly 50 answers. Chosen because results stay explainable and it works on tiny data. Rejected: collaborative filtering, matrix factorization, two-tower models and LightFM (they need other users' data, PRD §2.1); embeddings (PRD §9); sequence models such as SASRec (too little data); gradient-boosted ranking (overfits, hard to explain). No earlier session had chosen a model; this is the first decision on it.
55. **Answers to recommendations get their own table, planned but not built.** `recommendation_feedback` (with RLS) will store save, not for me, already know it, maybe later, too similar, more like this, less like this and loved it, each with a snapshot of the route and component scores shown. It is the training data for #54 and is not part of Stage 3.
56. **Score ties break on the candidate key.** `scoreCandidates` sorted by score alone, so equal scores kept arrival order, which depends on which catalogue call answered first. Ties now break on `candidateKey`, so the same library and candidates always give the same list (the invariant the future per-user model and the snapshots rely on).
57. **An anime feature is a film for time budgets.** Canon stores anime films with `runtime_minutes` and no episode runtime; `estimatedMinutes` read only the episode field, so a two-hour anime film estimated nothing and passed a 40-minute budget as "One episode". Anime with a runtime and no episode runtime now takes the film path.
58. **Each shown recommendation stores its component values.** `query_sessions.results` now carries the components (key, weight, value, contribution), adjustments and normalised weight as displayed. This is the feature snapshot RECOMMENDATIONS §14 needs for the later logistic regression; it is jsonb, so no migration, and the full Stage 3 contract in `docs/SPEC-STAGE3.md` §9 supersedes it when built.
59. **Founder answers to SPEC-STAGE3 §E (2026-09-17).** Every default confirmed except #9: the recency window for the "recently shown" filter is **14 days**, not the spec's 7 — `RECENCY_DAYS = 14` when the constant is written into `src/lib/taste/weights.ts`, and the spec's §A constant list and §9.2 example read with that number. Explicitly confirmed: music excluded from every Stage 3 candidate source (Q1); band thresholds 0.60/0.35 stay provisional until the first calibration run (Q2); Home keeps quotas 2/0/1 at L = 3 (Q3); the private score enters only through affinity, superseding #12's separate nudge (Q4); taps add no words and the mock extractor's DIMENSION_TAGS go (Q5); "not for me" stays out of the anti-profile in Stage 3, per #32 (Q6); creator expansion profiles up to 15 materialised rows per request, 5 inline and 20 per cron run (Q7); canon profiles are committed to the repository as generated code so tests run model-free (Q8); form is length only, craft words stored but not scored (Q10); category_stretch stays a phase component (Q11). The eleven §E questions are now closed; no remaining one blocks implementation.
60. **Stage 3 coding sessions run inside a fixed boundary.** At the founder's direction (2026-09-17), the AI sessions implement only the low-risk, deterministic Stage 3 layer — docs sync, vocabulary v2, weights/constants, the calibration utility, vector and form utilities, affinity/entry-vector plumbing, types, migration 0003, user-profile construction straight from the spec, deterministic fixtures, profiler interfaces with deterministic/mock behaviour only, and unit tests — and stop before the recommendation engine. The scoring pipeline, candidate generation, hard filtering, re-ranking, quotas and caps, bridge repair, the explainer, snapshot wiring, real canon profiling, calibration against real data, and any learned or Bayesian logic belong to the stronger-model sessions (Sol/Astra/Opus). Anything the spec does not explicitly answer is reported as a STOP, not decided. Approved deviations from SPEC §B's letter, all additive: the family-restricted similarity is added as a new export while the existing whole-vector similarity stays until the engine session; the `Route`/`Recommendation` type change is deferred because it would break the legacy engine today; `fitsTime`/`estimatedMinutes` stay in `recommend.ts` rather than moving to `form.ts`. Migration 0003 is written by the session and applied by the founder by hand in the Supabase SQL editor, after 0002 (still not applied live as of this date).
61. **Spec items superseded by SPEC-STAGE3.** With the founder's answers to §E (see #59), the following earlier calls no longer hold for Stage 3 and the spec governs: **#30** (components re-normalise over those with evidence) — replaced by the fixed denominator: every candidate is scored on all six components, a missing profile contributes 0, and no sum is ever a denominator; **#51** (readings may carry negative weights) — v2 readings are non-negative, with negation recorded in `absent` and `didnt_work`, and negative vector values mark the row failed; **#12** (private score as a capped ±0.05 sort nudge) — the private score now enters only inside `affinity(e)` (±0.135), and the separate nudge is gone; **form is length only** — the 0.15 form weight scores the length band (SPEC §1.4, §2.4), and craft words are stored but not scored; **music is excluded from Stage 3 candidates** (profiled, never matched, per #50 and §E Q1); **calibration** — the two family similarities map through committed provisional constants (cal-provisional) until the script runs against a profiled population of ≥ 60 items, nearest-rank P10/P90 over exhaustive or seeded pairs (SPEC §3); **band thresholds 0.60/0.35** are provisional constants and part of feature_version (§E Q2).
62. **Vocabulary v2 lands as additive code with the version pinned.** The v2 word lists, the two family group-weight tables (G_STORY, G_FEELING), `familyOf` and per-family `isKnownKey` ship now, but `VOCABULARY_VERSION` stays `"v1"` — pinned until the extractors emit v2 in the same commit. Four write paths stamp that constant onto live rows (server/extraction.ts, extractor.ts, nvidia.ts, mock-extractor.ts) and the re-read route keys off `extractor`, not version, so bumping early would mislabel real data permanently with no self-heal. v2 vocabulary keys do not collide with v1 keys except inside `theme` (found-family moved to bond), which no live row carries at scale; the extractors' emitted shape is unchanged until the Stage 3 extractor work.
63. **The calibration sampler's xorshift is a fresh 32-bit one, committed and pinned by seed.** SPEC §3.3 says "the existing xorshift generator" but the repo contains none — the only seeded hash is the unexported `daySeed` FNV in `recommend.ts`, and sampling one million pairs needs a PRNG, not a hash. Rather than touch a protected file or invent a dependency, `calibration.ts` ships its own `xorshift32` (non-zero state, mulberry-style output scaling to [0,1)), seeded with 20260915 as specified. The sampled behaviour the spec pins — seed, pair count, uniqueness, i ≠ j, reproducibility — is implemented exactly and tested (N = 1501 twice → identical constants); only the internal stream differs from a generator that never existed. The script session can swap the stream in one place without touching any behavior the spec defines.

64. **Four Stage 3 invariant corrections before v2 integration (2026-09-19).** A pre-integration cleanup pass fixed the reviewed foundation issues: **(1)** the anti-profile counts evidence per family as distinct evidence IDs (`entryId:dropped`, `entryId:doesnt_hit`, one `entryId:didnt_work` per affected family for all of one entry's `didnt_work` keys collectively) and a family becomes non-null only at `ANTI_MIN_EVIDENCE` distinct IDs of that family — one note naming two disliked keys is one piece of evidence, not two, while each valid key still blends as its own one-hot part; `anti.evidence` stays the global count of distinct `(entryId, source)` pairs. **(2)** `blend()` averages all five reading scalars (`intensity`, `ache`, `pace`, `moral-complexity`, `complexity`) defined-only, via the existing `READING_SCALARS` constant, so a v2 story scalar the other side omits is no longer diluted like a zero-valued word attribute; word keys still count missing as zero. **(3)** `familyOf` resolves only exact v2 keys (grouped keys carry exactly one dot and a listed value; bare scalars only in their own family), `isKnownKeyIn` is defined as `familyOf(key) === family`, and the anti-profile accepts a `didnt_work` key only when it validates — malformed or unknown keys neither route nor count as evidence; v1 `isKnownKey` is untouched. **(4)** `PROFILED_CATEGORIES` is all five media (the founder decision in #50 was that all five are profiled, four matched) with a new readonly `MATCHED_CATEGORIES` for the four matched in Stage 3; no consumers of the old export existed. `VOCABULARY_VERSION` stays `"v1"` (#62), `RECENCY_DAYS = 14` (#59) and the v1 engine are untouched.

65. **Vocabulary v2 is now the active extraction contract, with v1 retained as immutable history (2026-09-19).** This closes the pin in #62 atomically: mock, Claude and NVIDIA emit the §1.3 `Reading` shape and `{story, feeling}` vector; new queue rows are stamped `v2`; pending workers process only the current version; and re-read creates a v2 row per reaction rather than relabelling or overwriting its v1 row. Taps never add words, and a reaction with no written note produces an empty reading without a model call. Negated lexicon matches route to `absent`; explicit dislike evidence routes to `didnt_work`; `valued`, `didnt_work.phrases` and `quote` are guarded as verbatim substrings. Historical v1 and current v2 rows load together. Until the Stage 3 scorer replaces the legacy engines, v2 feeling plus v2 theme evidence is deterministically projected into their old flat space; this compatibility projection is not a new scoring model. An empty family vector is missing evidence, not a present profile/reading. Negative or out-of-range reading values are rejected, never clamped. No recommendation scoring, candidate, re-ranking, explanation or UI policy changed in this cutover.

67. **Item profiler: NVIDIA Nemotron is the runtime default, and the mock reuses the note lexicon (2026-09-22).** Founder's calls, closing STATE "Blocked #1". The Claude and NVIDIA profilers share one interface and prompt. `AI_PROVIDER` selects between them as it does for extraction, and NVIDIA is the default because it is the provider already configured. The deterministic mock profiler runs the existing, reviewed `lexicon.ts` rules (already v2 keys) over the item's catalogue overview, plus `frameFromGenre` and the form length band. No new word list is invented. Mock profiles are placeholders for offline tests, never presented as real readings of a work.

68. **Craft words are closed per-category lists in vocabulary.ts (`CRAFT`, `isCraftKey`), implemented exactly from ATTRIBUTES §1D.** No `VOCABULARY_VERSION` bump: the words were already part of the v2 specification, they have never appeared in any reading, and they never enter a vector.
69. **Frame merge keeps the catalogue attribute on a weight × confidence tie and caps merged frames at 3** (the §1.2 cap), by weight × confidence then key. The spec named the winner rule but not the tie or the post-merge cap.
70. **For music items, AI-sourced attribute confidence is capped at 0.5,** per #50 and ATTRIBUTES §1D. Music isn't matched in Stage 3, so this only affects stored data.
71. **Premise praise/reception guard: a premise containing a reception word is dropped to null rather than failing the profile.** §1.2 forbids praise words and #53 forbids reception, but losing a whole profile over one word is disproportionate.
72. **AI profiles are validated strictly (exactly one stakes, exactly one ending, all five scalars) and fail otherwise.** The deterministic mock is validated leniently, because a lexicon can't honestly assert an ending. A mock profile is a placeholder, and Session 4 must never persist one as though it were real without an explicit decision.
